== 2. Convention `publishing` paramétrable (0.0.9)

Le bloc `publishing` dupliqué dans chaque module porte l'identité POM
(licence + developer). Appliquer la convention telle quelle aurait fait
publier les modules **propriétaires** sous Apache-2.0 / `cccp-education`.

Livré :

* `PublishingIdentity` — **objet pur** (licence + developer), politique de
  repli testable : une surcharge vide/blanche retombe sur le défaut cccp,
  les valeurs sont trimmées ;
* `PublishingConventionsExtension` étendue : `licenseName`, `licenseUrl`,
  `developerId`, `developerName`, `developerEmail`, `website`, `vcsUrl`
  (tous `null` par défaut = comportement historique) ;
* `PublishingConventionsPlugin` applique l'identité résolue et respecte
  `website`/`vcsUrl` explicites (précédence sur `gradlePlugin.*`) ;
* preuves : 5 UT `PublishingIdentityTest`, 1 FT TestKit « identité
  propriétaire » (POM généré, absence de `cccp-education`), 1 scénario BDD
  `publishing-conventions.feature` ;
* **pin BOM de test** `0.0.59 → 0.0.124` (dernière version publiée vérifiée
  repo1 HTTP 200) + `WorkspaceBom.FALLBACK_VERSION` + garde UT.

`conventions-plugin` **0.0.9** : `compileKotlin` / `compileTestKotlin` /
`compileFunctionalTestKotlin` VERTS, `publishToMavenLocal` VERT (signé GPG).

== 6. Leçons

* Un « borough liquidé » peut rester **très** en retard sur sa propre vision ;
  la clôture d'EPICs mesure l'outil, pas son adoption.
* Une convention qui hardcode l'identité cccp **bloque** l'adoption des builds
  propriétaires : la paramétrisation est un prérequis d'adoption, pas une
  feature.
* L'audit d'ouverture doit mesurer le **workspace** (grep cross-borough), pas
  seulement le dépôt : c'est ce qui a révélé 0/27 privés et le pin BOM périmé.
