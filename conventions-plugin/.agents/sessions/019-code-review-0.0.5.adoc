== Findings

=== 🔴 P1 — Aucun CI dans le repo

`conventions-gradle` n'a **pas** de `.github/workflows/`, contrairement à ses
consommateurs (bakery, capsule, codebase ont `test.yml`). C'est le seul borough
sans CI alors qu'il est le socle de tous. Avec la règle « Local = Build,
Tests = CI », ce borough n'a **aucune preuve de validité exécutable** hors local.

=== 🔴 P1 — `configureKover` no-op silencieux

`KoverConventionsPlugin.kt:27-62` configure Kover par réflexion
(`invokeMethod` ×13, `catch (Exception) → null`). L'API Kover expose
`currentProject` en getter (`getCurrentProject()`) et en fonction à 1 paramètre
(`currentProject(Action)`). Le code cherche `name == "currentProject" &&
parameterCount == 0` → matche le getter, puis tente `sources`/`includedSourceSets`/
`reports`/`total`/`html`/`xml`/`onCheck`, absents sur cet objet → `null` en
chaîne, **tous les échecs avalés**. Résultat : `includedSourceSets` et `onCheck`
ne sont **jamais** configurés. Seul `koverThresholdCheck` fonctionne (il lit le
XML). Bug **documenté mais non corrigé** par le commit `a7db92f`.

=== 🟠 P2 — `additionalTasks` Cucumber non câblées à `check`

`CucumberConventionsPlugin.kt:52-54` câble uniquement `cucumberTest` à `check`.
Les `CucumberTaskSpec` supplémentaires (22 chez capsule, runners focalisés) ne
sont **pas** dans `check` — ils sont lancés manuellement par la CI
`full-tests.yml`. `./gradlew check` ne couvre donc pas la majorité des scénarios
Cucumber d'un consommateur.

=== 🟠 P2 — Drift fallback vs catalogue

`TestDependencies.kt:19` : `WORKSPACE_BOM_COORDINATES = education.cccp:workspace-bom:0.0.13`
alors que le BOM publié réel est **`0.0.58`** (45 versions d'écart). Fallback
`assertj` `3.27.7` vs catalogue local `3.25.3`. Fallback `detekt 1.23.8`
(abandonné sous Java 25).

=== 🟡 P3 — Config cache vs `startParameter` muté

`GradlePluginConventionsPlugin.kt:53` : `project.gradle.startParameter.isBuildCacheEnabled = true`
muté dans `apply()`, hostile au configuration cache activé par ailleurs.
`buildCache { local { isEnabled = true } }` serait correct.

=== 🟡 P3 — Assertions BDD factices

8 `assert(true) // verified by ... source` dans `GradlePluginConventionsSteps.kt`
(defaults d'extension, override DSL, jvmArgs) — les scénarios passent sans rien
vérifier sur la partie la plus critique (defaults de config).

=== 🟡 P3 — `check.dependsOn(detekt)` fragile + detekt skippé Java 25

`LintConventionsPlugin.kt:15-27` : detekt **silencieusement skippé** sous Java 25
(le toolchain du workspace) → la convention `lint` ne fait **que ktlint** en
pratique. `project.tasks.findByName("check")?.dependsOn(...)` peut être null
selon l'ordre.

=== 🔵 P4 — Traçabilité release

Pas de tag git malgré 5 versions publiées ; version hardcodée
(`build.gradle.kts:10`) ; BOM `0.0.58` contraint encore
`conventions-plugin:0.0.4`.

== Verdict

Architecture **saine** : DDD, `KoverCoverage` objet pur testable, DSL propre,
~1200 lignes de build supprimées côté consommateurs, adoption réelle 15/23.
Mais la gouvernance (« borough LIQUIDÉ, maintenance réactive ») **contredit le
code** : pas de CI, un bug production `configureKover` non corrigé, des runners
non couverts par `check`, des fallbacks périmés.

**Recommandation** : traiter P1 (CI + `configureKover`), puis P2 (câblage
`additionalTasks` à `check` ou opt-in documenté). P3/P4 = dette acceptable.
