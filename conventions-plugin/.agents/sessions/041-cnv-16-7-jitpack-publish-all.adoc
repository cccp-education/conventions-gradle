== Mission

Demande pilote : « c'est bon tous les plugins et libs seront publiés sur
jitpack ? » puis « lance ». Publier sur JitPack **tous les artefacts publics**
(plugins et libs), dans l'ordre DAG N0 → N1 → N2, sans passer par Sonatype ni
le Gradle Plugin Portal.

== 1. Recette appliquée

`jitpack.yml` à la racine de chaque dépôt :

[source,yaml]
----
before_install:
  - sdk install java 25.0.5.0+8-tem
  - sdk use java 25.0.5.0+8-tem
install:
  - ./gradlew -p <sous-build> publishToMavenLocal
env:
  CI: "true"
----

* `workspace-bom` publie le BOM/catalogue + les **9 contrats** (10 commandes
  `-p`), car ce sont des builds autonomes.
* `video-kernel-gradle` a deux sous-builds : le `install` publie **un seul
  artefact selon le tag** (`VERSION` = `0.7.0` ou `0.0.2`).
* **Correctifs signature** (même verrou que S-038) : `academy-plugin`,
  `dashboard-plugin` et `bureau-plugin` appliquaient `signing` directement ;
  `plugin-publish` auto-signe alors même en `CI=true`. `signing` est désormais
  appliqué **conditionnellement** (`!jitpackBuild && (CCCP_PUBLISH || !CI) &&
  non SNAPSHOT`).

== 5. Blocage `video-kernel` / `youtube-auth`

Les deux builds JitPack échouent **avant** Gradle :

----
Downloading: java 25.0.5.0+8-tem
Download has failed, aborting!
Can not install java 25.0.5.0+8-tem at this time...
-> Gradle runs with JVM 8 -> "Gradle requires JVM 17 or later"
----

C'est un **échec transitoire/rate-limit du CDN SDKMAN côté JitPack** (les 20
autres builds ont installé le même JDK sans problème ; des `429` ont aussi été
observés). La recette est prête ; il suffit de **rejouer** les tags `v0.7.0`
et `v0.0.2` quand la limite est levée. Aucun force-push de tag (non demandé).
