== 1. Famille 1 — Test JUnit Configuration (present dans ~20 projets)

=== Pattern actuel

[source,kotlin]
----
dependencies {
    testImplementation(kotlin("test-junit5"))
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

tasks.withType<Test>().configureEach {
    useJUnitPlatform()
    testLogging {
        events("passed", "skipped", "failed")
        showStandardStreams = true
    }
}
----

=== Projets concernes

Tous sauf `intellij-plugins` (JetBrains Platform, pas Gradle). Soit ~20 projets.

=== Variantes identifiees

|===
| Variante | Projets
| `jvmArgs("-XX:+EnableDynamicAgentLoading")` ajoute | bakery, plantuml, codebase, capsule
| `maxHeapSize = "2g"` | codebase, plantuml
| `systemProperty("junit.jupiter.execution.parallel.enabled", "true")` | codebase seulement
|===

=== Convention plugin propose

`education.cccp.build.gradle-plugin` — avec options :
- `enableDynamicAgentLoading` (default true)
- `maxHeapSize` (default null)
- `parallelExecution` (default false)

== 2. Famille 2 — FunctionalTest Source Set (present dans ~12 projets)

=== Pattern actuel

[source,kotlin]
----
val functionalTest: SourceSet by sourceSets.creating {
    java { srcDirs("src/functionalTest/kotlin") }
    resources { srcDirs("src/functionalTest/resources") }
}

dependencies {
    add(functionalTest.implementationConfigurationName, gradleTestKit())
    add(functionalTest.implementationConfigurationName, kotlin("test-junit5"))
    add(functionalTest.implementationConfigurationName, libs.assertj.core)
    add(functionalTest.runtimeOnlyConfigurationName, "org.junit.platform:junit-platform-launcher")
}

val functionalTestTask = tasks.register<Test>("functionalTest") {
    testClassesDirs = functionalTest.output.classesDirs
    classpath = configurations[functionalTest.runtimeClasspathConfigurationName] + functionalTest.output
    useJUnitPlatform()
}

gradlePlugin.testSourceSets.add(functionalTest)

tasks.check { dependsOn(functionalTestTask) }
----

=== Projets concernes

bakery, plantuml, codebase, codex, capsule, readme, slider, hyperframes, dashboard, graphify, api-key-pool, planner

=== Variantes identifiees

|===
| Variante | Projets
| `configurations["functionalTestImplementation"].extendsFrom(…)` legacy | capsule, readme
| `testImplementation` extend `functionalTest` (reverse inheritance) | plantuml, readme
|===

=== Convention plugin propose

`education.cccp.build.functional-test` — parametres :
- `sourceSetName` (default `functionalTest`)
- `additionalDependencies` (pour les depends specifiques projet)

== 3. Famille 3 — Cucumber BDD Tests (present dans ~8 projets)

=== Pattern actuel

[source,kotlin]
----
sourceSets.test {
    resources.srcDir("src/test/features")
    java.srcDir("src/test/scenarios")
}

val cucumberTest = tasks.register<Test>("cucumberTest") {
    testClassesDirs = sourceSets.test.get().output.classesDirs
    classpath = configurations.testRuntimeClasspath.get() +
        sourceSets.test.get().output +
        sourceSets.main.get().output +
        files(tasks.jar.get().archiveFile)
    useJUnitPlatform { excludeEngines("junit-jupiter") }
    systemProperty("cucumber.junit-platform.naming-strategy", "long")
}

tasks.named<Test>("test") {
    filter { excludeTestsMatching("*.scenarios.*") }
}

tasks.check { dependsOn(cucumberTest) }
----

=== Projets concernes

codebase, bakery, plantuml, slider, readme, capsule, dashboard, agent-contracts (workspace-bom)

=== Variantes identifiees

|===
| Variante | Projets
| `cucumber.execution.parallel.enabled` | codebase
| Timeout 5min par scenario | bakery
| 32 cucumber tasks parametrees (data class CucumberTaskSpec) | codebase (unique, le plus avance)
| Plugins Cucumber (`io.cucumber:junit-platform-engine` 7.21.0) | tous
|===

=== Convention plugin propose

`education.cccp.build.cucumber` — parametres :
- `featuresDir` (default `src/test/features`)
- `scenariosDir` (default `src/test/scenarios`)
- `parallel` (default false)
- `timeoutMinutes` (default null)
- Support multi-task pour le pattern avance codebase

                }

                    connection.set(gradlePlugin.vcsUrl.get())
                    developerConnection.set(gradlePlugin.vcsUrl.get())
                    url.set(gradlePlugin.vcsUrl.get())

                project.findProperty("relocationGroup")?.let { targetGroup ->
                    withXml { /* inject relocation */ }
                }

        }
    }

    if (System.getenv("CI") != "true" && !version.toString().endsWith("-SNAPSHOT")) {

| `create<MavenPublication>("maven") { from(components["java"]) }` | librairies pures

|===

=== Convention plugin propose

`education.cccp.build.publishing` — parametres :
- `publicationType` (PLUGIN | LIBRARY | BOM)
- `signingEnabled` (default true)

== Architecture Decision Records

=== ADR-001 — Pourquoi un plugin binaire publié et pas un `buildSrc`/`includeBuild` partagé ?

*Contexte* : les convention plugins sont écrits en plugins binaires
(`src/main/kotlin/build/*.kt`, `java-gradle-plugin`) — pas en precompiled
script plugins `.gradle.kts`. Alternatives : `buildSrc/` (impossible
cross-repo), `includeBuild()` (couplage par chemin local, incompatible avec la
CI et avec les dépôts privés), « trop tôt pour publier » (hypothèse du
cadrage initial, invalidée par 26 boroughs consommateurs).

*Décision (révisée 2026-11-03, S-024 — l'ADR initial décrivait
`includeBuild()` + precompiled scripts, ce qui n'a jamais été la réalité)* :
plugin **binaire publié** sur Maven Central (+ Gradle Plugin Portal), consommé
par identifiant et **version explicite** :

[source,kotlin]
----
plugins {
    id("education.cccp.build.gradle-plugin") version "0.0.9"
    id("education.cccp.build.publishing") version "0.0.9"
}
----

*Conséquences* :
* aucune modification de `settings.gradle.kts` n'est requise (hors
  `pluginManagement` vers `mavenCentral()` / Portal) ;
* une **session parallèle** sur un consommateur n'est jamais bloquée par une
  modification locale du plugin : consommer exige une **publication** (ordre
  DAG `plugin → Central → BOM/catalogue → consommateurs`) ;
* la CI d'un consommateur ne résout que des artefacts publiés — un pin vers
  une version non propagée est un faux vert local (mavenLocal) et un rouge CI
  (constat S-024 sur `payment-scaffold`) ;
* l'identité POM est **paramétrable** (`publishingConventions { … }`, 0.0.9) :
  un consommateur non-cccp (propriétaire) ne peut plus être relicencié par
  accident en adoptant `publishing`.

=== ADR-003 — Adoption par lots, un borough par session

*Contexte* : la vision « 1 source de vérité » mesurait l'outil, pas son
adoption (S-024 : 0/27 builds privés adoptants).

*Décision* : EPIC **CNV-13** découpé en lots — L1 `payment-scaffold`
(16 modules), L2 privés MVP0 (`training` → `workspace` → `waiter` → `quizz`),
L3 rollout public 0.0.9 + catalogue MEMPHIS, L4 outillage (garde
cross-borough, arbitrage `kover`/`logback-exclusion`). Un seul sessionneur par
borough ; preuve = CI verte du dépôt migré.

*Conséquence* : chaque lot est une session livrable et vérifiable ; le
catalogue MEMPHIS n'est bumpé qu'après publication de la version consommée.

=== ADR-002 — Ordre de migration

1. Dashboard-gradle (projet nouveau, CNV-5 dogfood) — valide les 3 patterns (nouveau projet)
2. Codebase-gradle (projet existant mature) — valide la compatibilite ascendante
3. Capsule-gradle (projet legacy, patterns divergents) — valide la migration des cas tordus
4. Generalisation aux 15+ autres projets
